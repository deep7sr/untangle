POC architecture

How a plain-language question becomes a read-only diagnosis with evidence, on the 8-device lab.

For architecture review Branch demo/agentic Date 12 October 2026 Prepared by Deependra Singh Rajput

One investigation, step by step

  1. The engineer types a question in the web UI.
  2. The UI posts it to the API. The API starts a run and streams every step back live.
  3. Code looks up approved past cases that resemble the question and passes at most three as hints. Hints are never evidence.
  4. The agent sends the instructions, the list of live skills, the hints and the question to the LLM. The LLM answers with a tool to call and a one-sentence reason.
  5. Code checks the call before it leaves: at most 16 calls per reply, and only IP addresses seen in the question or in earlier results. Each allowed call gets an evidence id (E1, E2 and so on).
  6. The call goes over MCP to one of two servers: Topology (what the graph knows) or Network (what the devices say now). The result returns to the LLM, which picks the next check. Steps 4 to 6 repeat.
  7. For a device check, the Network server sends one allow-listed, read-only command to the device console and cleans the output (figure 2).
  8. When the evidence explains the problem, the LLM writes a structured report that cites evidence ids.
  9. Code checks the report: citations that do not exist are removed, and the confidence (high, medium or low) is computed from the evidence. The engineer sees it and can reply to continue the conversation.
  10. After a diagnosis, code drafts a case. An engineer approves, corrects or rejects it. Approved cases are stored in the graph and feed step 3.

What the design guarantees

  • The LLM never writes a device command. It picks a tool; the command comes from a file reviewed by the network expert.
  • Read-only, checked twice. Only show and ping can reach a device: first the allow-list, then a guard that refuses anything else.
  • Secrets stay inside. Passwords and keys are removed from device output before it is stored, shown or sent to the LLM.
  • Every fact cites a check. A report can only cite evidence ids that exist, and the confidence is computed by code.
  • People approve the knowledge. Skills and cases are reviewed by engineers. They steer an investigation and never count as evidence.
  • The network model is built by code. Discovery reads the devices through the same Network server and writes the graph, with no LLM involved.

Not yet proven

  • Latest features with a real LLM. Conversation, cases, hints and the skills editor pass their code tests but have not run against a live model yet.
  • More than one path. The lab has a single path between the sites. The route trace follows only the first of several equal-cost paths.
  • Scale. Everything has run on 8 devices only.

Open points for review

  • Is Neo4j allowed at UST, or should the graph live in an existing tool?
  • Which LLM endpoint for the demo? The company Azure deployment is reachable only from the UST network.
  • Is read-only the agreed scope for phase 1? It has not been confirmed since the redesign.
